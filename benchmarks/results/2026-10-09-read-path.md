# Student read path: where the CPU goes, and four fixes (P14.2, P14.3) — 2026-10-09

Scenario B (result day: config → me → latest → stats → 30% history, per student) is limited by API CPU
first, on the laptop and on the GitHub runner alike (2026-10-08-k6-scenarios-A-B.md, P14.1). This file
answers two questions: what that CPU is spent on (a profile), and what each change bought (before/after
on the same machine, back to back).

## 1. Profile: top bottlenecks (P14.2)

**Source:** py-spy (`record --format raw --subprocesses`, 100 Hz) of the API container. It ran 90 s into
the first scenario-B pre-authenticated run of `perf.yml` run 37737458557.
- Commit 1e3b76b, before any of the changes below.
- GitHub runner: 4 vCPU Intel Xeon 8370C, 16 GB. One API container with 2 Uvicorn workers; k6 on the same
  machine.
- 18,275 samples, split evenly between the two workers.
- Raw file: `py-spy-B-preauth-1.txt` in the run's artifact.

"Self" is the share of samples whose innermost frame is in that code. "Inclusive" is the share with that
code anywhere on the stack. Categories are counted in table order, so no sample counts twice.

| # | What | Self | Inclusive | Evidence |
|---|---|---|---|---|
| 1 | **SQLAlchemy + asyncpg**: building statements, executing them, loading rows | **38.7%** (SQLAlchemy 24.0%, asyncpg 14.7%) | 44.2% | Top leaves: `asyncpg prepared_stmt.__do_execute` 6.6%, `connection.execute` 4.5%, `greenlet_spawn` 3.1%, `cache_key._generate_cache_key` 1.4%. JSONB decoding of snapshot payloads (`_jsonb_decoder` → `json.loads`) is another 2.7%. |
| 2 | **Opening a transaction per request**, even when nothing else needed the database | — | **5.0%** in `UnitOfWork.set_tenant` alone, plus BEGIN/COMMIT | Every request's unit of work ran `SELECT set_config('app.tenant_id', …)` when it opened, inside a transaction it then committed, whether or not the route queried anything. |
| 3 | **Route matching**: FastAPI testing patterns router by router | **6.1%** (`_match` 3.1%, `matches` 3.0%) | 8.1% | 158 operations in 23 routers. `config` and `me` were already 3rd and 1st, but the student results router was 18th of 23 (marksheets 20th, inbox 22nd, verification 23rd), so `latest`, `stats` and `history` tested most of the admin surface first. |

Smaller costs, for scale:
- **HTTP server** (uvicorn, httptools, asyncio streams): 10.6%. This is the floor of doing HTTP in Python.
- **FastAPI dependency resolution:** 7.0%.
- **Redis client:** 4.4% (sessions and the tenant cache).
- **structlog:** 2.0%.
- **Prometheus:** 0.9%.
- **The event loop itself:** 8.7%. With uvloop it shows as `asyncio.run`, not as idle, so it isn't waiting time.

**Why #1 is mostly waste:** the rows the student path reads are immutable or nearly so. Published
snapshots and frozen statistics are protected by triggers. A user is linked to a student once. The live
publication list changes only on publish or withdraw. Yet every request loaded them again through the ORM.

## 2. Fixes, measured one at a time (P14.3)

**Instrument:** `backend/scripts/measure_read_path.py`. It runs the k6 journey through the real
application over an in-process ASGI transport, as 200 students of the `loadtest` tenant (8,000 students,
one six-paper exam, from `loadtest_data.py`), 20 at a time, for at least 3,000 requests after one warm-up
journey per student.
- There is no network, proxy or load generator, so it isolates the API's own work.
- It reports process CPU time per request (the number scenario B is limited by), throughput on one event
  loop, and SQL statements sent per request.
- Machine: the M2 laptop (4P+4E cores) **on battery with Low Power Mode**. Absolute numbers aren't
  comparable to the AC or runner results. Each comparison below ran back to back on the same machine in
  the same state, alternating variants. The ranges are the spread over the runs.

| Change | Commit | Before | After | CPU per request |
|---|---|---|---|---|
| **A. Student read cache** (`publishing/read_cache.py`): cache the session's student id, the live publication list (5 s, dropped after commit on publish/withdraw), snapshot payloads and statistics (immutable), and the stats level (30 s). Keys are per tenant, and per student where it matters. | b0f6c4b | cache off: 6.75–7.02 ms · 133–145 req/s | cache on: 5.48–5.56 ms · 173–177 req/s | **−20%** |
| **B. Student routers first** (`web/routes.py`) | this commit | 5.62–5.64 ms · 169–172 req/s | 5.31–5.36 ms · 180–184 req/s | **−5%** |
| **C. A unit of work opens its transaction at its first statement** (`core/db.py`): `set_config` runs as the transaction's first statement, from the session's `after_begin` event, so a request answered from cache checks out no connection at all. | this commit | 5.36–5.61 ms · 170–182 req/s · **1.23–1.24 SQL statements per request** | 4.60–5.12 ms · 174–214 req/s · **0.48–0.50 SQL statements per request** | **−14%** (median of 4 runs each: 5.46 → 4.69 ms) |

| **D. Ping a pooled connection only after it idled** (`core/db.py` `_ping_if_idle`, replacing `pool_pre_ping`). With asyncpg every pre-ping was BEGIN, `;` and ROLLBACK: on the runner, 638,000 of the 1.27 million BEGINs in `pg_stat_statements` were pings, and they cost 2.6% of API CPU (py-spy). | this commit | 4.64–4.66 ms · 213–214 req/s · per run (about 3,700 requests with warm-up) BEGIN 2,144–2,524, ROLLBACK 942–1,134 | 4.50–4.53 ms · 220–221 req/s · BEGIN 1,135, **ROLLBACK 0** | **−3%** |

- **Runs:** A ran 2 times per variant at 3,006 requests, plus one off-run at 2,057. B ran 2 times per
  variant. C ran 4 times per variant, alternating.
- **D:** 2 runs per variant, alternating. Database counts come from `pg_stat_statements` on the local
  database, reset before each run, because pings bypass SQLAlchemy's statement hook.
- **All four together:** about 6.9 ms down to 4.5 ms of API CPU per student request, **about 35% less**
  on this machine.

What changed besides CPU (C):
- Statements per request fell by 60%. That count excludes BEGIN and COMMIT, which asyncpg sends outside
  the statement hook, so database round trips fell further.
- In-process p50 wall time for `config` fell from about 265 ms to about 25 ms. With 20 students at a time
  and a pool of 10 connections (plus 5 overflow), requests had been queuing for a connection they didn't need.

Why each is safe:
- **A.** Isolation is covered in `read_cache.py`'s docstring and `test_read_cache.py`: keys never mix
  tenants or students, and a withdrawal applies at once in the process that made it.
- **B.** Order only matters where two patterns could match the same path. The student routers' prefixes
  (`/api/v1/me/...`, `/api/v1/verify/...`) don't overlap the admin ones. The full suite (505 tests),
  including the route-sweeping authorization matrix, passes.
- **D.** Only connections idle for more than a second, when a restart or an idle timeout could have
  closed them unseen, are pinged, and a dead one is replaced before use. One that dies mid-burst fails
  that request with a retryable 503 and the next one recovers. Pre-ping didn't cover that case either: a
  connection can die between the ping and the query. Three tests cover it in `test_outages.py`, killing
  pooled connections with `pg_terminate_backend`. Mutants caught: never pinging fails 2 tests, and
  pinging every checkout fails 2.
- **C.** RLS still fails closed. Two mutants were run:
  - Without the `after_begin` hook, 11 kernel tests fail.
  - Binding eagerly again fails `test_a_unit_of_work_takes_no_connection_until_its_first_statement`.
  - A tenant bound after the transaction has begun (sign-up checks the slug first) is still set on the
    spot.
  - After commit the context is cleared as before, so a later transaction in the same session has none.

### Still on the read path, not changed
- **`/me` reads the `users` row on every call** (its display name and two-step status). That is the 0.5
  statements per request left. Caching it means invalidating on name, email and two-step changes in every
  process. It's the next candidate if scenario B on real hardware still needs it.
- **SQLAlchemy ORM overhead on cache misses.** First reads after publication, and history pages, still
  pay for statement compilation and ORM row loading. Core `select()` of columns, as `StudentReads` does,
  is the pattern to copy.

## 3. What this does not show
- **Recovery from a Postgres restart under load with D in place.** It is re-run with `perf.yml`
  `chaos=postgres` and will be recorded here; the earlier result (2026-10-08-failure-under-load.md)
  used pre-ping.
- **Throughput under k6 on the runner.** These are in-process numbers. That scenario-B req/s moves by
  similar ratios on the 4-vCPU runner needs `perf.yml`'s same-machine compare (P14.4). Two runs on two
  runner CPU models can't be compared (Intel 8370C against AMD 7763, seen on 2026-10-08).
- **Database-side savings** (fewer round trips per request, fewer connections busy) as measured by
  `pg_stat_statements`. That also needs the runner compare.
